# 固定存档码、完整历史与免账号恢复

## 使用方式

房间创建时获得永久 `roomId` 和固定的 26 位存档码，六位房间号仍用于联机邀请。每次成功提交自动保存完整进度，房间菜单“存档”只给当前保存点添加手动标记与可选备注，不暂停游戏，不改变固定码。重复标记同一版本更新备注，时间线保留每次标记记录；保存点时间表示原局面提交时间，标记时间可在时间线查看。

首页“历史与恢复”、房间“历史回顾”打开 `/archives`。可以按对局、行动编号、操作类型筛选时间线，点击记录查看该次提交完成后的只读棋盘与资产；手动保存点单独列出。一次操作内的多个事件按真实执行顺序保存，首期不提供中间效果动画。

同一浏览器保留玩家会话时，原房间仍自动恢复原席位。使用固定码恢复时，选择最新或历史进度、自己使用的保存角色，系统另建房间；恢复者成为新房主，朋友加入后申请角色，由房主批准。完成分配后点击“继续对局”，沿用现有行动者及交易回应者离线等待规则。恢复大厅解除暂停后，仍可按原大厅规则加入新玩家。

固定码是共享查找与恢复凭证；拿到码的人可以另建恢复房间，不另设账号、个人恢复码或独立存档管理员。系统恢复游戏角色与状态，无法证明申请人是原来的现实玩家，不根据昵称自动认领。原房间与原历史保留，恢复房间提供“查看来源历史”入口。

## 标识与数据

| 标识 | 含义 |
| --- | --- |
| `code` | 六位联机号，首期保留所有已有号码，不实现回收 |
| `roomId` | 永久房间 UUID，历史与身份的关联键 |
| `archiveCode` | 服务端生成的固定 26 位码，数据库唯一索引兜底，随机碰撞重新生成 |
| `gameId` | 每局及恢复分支独立的对局 UUID |
| `snapshotId` | 房间与提交版本对应的不可变保存点 UUID |

编码字符集排除易混淆字母，查询兼容大小写、空白和分组连字符，展示分为 5／5／5／5／6 位。

在原 `rooms`、`sessions` 中增加 `room_id`，保留六位号接口及原命令回执语义。新增三表：

- `room_archives`：永久标识、固定码、联机号、恢复来源、请求去重资料。
- `room_snapshots`：完整内部状态、保存时公开投影、版本、对局、格式版本、规则摘要和手动标记。
- `room_history`：顺序、关联保存点、当时角色昵称、行动与阶段、行为类型、公开说明及仅服务端保存的内部明细。

创建、玩家或访客加入、准备、开局、成功操作、角色申请与分配、确实改变状态的连接和离线修复都保存进度。领域层补充行动边界、骰子、抽取内容、效果、灾害及补偿、终局事实。`HistoryTrace` 在提交作用域内收集，再批量追加到数据库，不在效果循环里查询数据库。

历史和手动保存点采用倒序游标分页，每页 50 条；游戏列表按 `gameId` 批量汇总。实时推送继续只发送最新状态，实时动态仍限制为最近 100 条；再开一局清空的只是当前页面动态。

## 一致性、隐私与恢复

Flowable 推进、房间状态、命令回执、历史和完整快照加入同一 InnoDB 事务。失败整体回滚，提交后才替换内存与推送；重复命令返回原回执，不重复记录。

历史接口只读取保存时的公开投影和事实白名单，不重新计算现金与净资产，不返回内部快照、手牌、内部报价对象、访客令牌摘要或原始操作明细。已发起报价的双方与现金、地产、抵债约定，以及同意、拒绝、取消、实际结算结果属于公开事实，通过原公开日志写入完整历史，玩家和观众均可查看。完整内部状态仅服务端恢复时使用；分配到角色后，其本人才能收到该角色的私人数据。

恢复复制地图、资产、位置、手牌、行动顺序、pending、trade、剩余效果与已确定结果，生成新房间及对局标识，清除旧会话、连接状态与申请。正在进行的快照通过 BPMN 恢复分支直接建立等待任务，重新绑定流程实例和任务，不重复开局、掷骰、抽取或结算。分配期间暂停推进，暂不自动转交房主；继续后恢复原规则。

角色批准在房间锁和事务中进行，撤销旧角色会话，再绑定申请人的访客身份。提交后立即撤销旧连接权限，沿用原认证清理窗口关闭连接，让房主交接自己的席位时仍能收到成功回执。纯观战、待分配访客和玩家在浏览器中分别保存；会话按 `roomId` 建键，兼容旧六位号键。

恢复请求以源房间与请求 UUID 去重；请求内容变化时拒绝复用 ID。会话由源固定码、随机请求 UUID、新房间 UUID 通过 SHA-256 派生，重试返回同一房间及会话，不保存原始令牌，不重复追加历史。角色已交接或移出时，旧请求不能取回被撤销身份。

保存点独立记录格式版本和四类玩法 JSON 的规范化 SHA-256 摘要，保留数组顺序并排序对象键。恢复要求当前格式，规则摘要相同或属于已明确支持的兼容变化；不兼容快照仍可回顾并显示原因。现有原房间的重启与后续配置使用方式不因档案摘要而改变。

2026-10-15 路障范围扩展额外兼容上一提交 `e95cc4c` 的默认规则保存点：旧规则摘要 `46709d3ca47ef8ad32dca845b91bcb56f929fae9eb15f0e9d9b6c2d5067b7ed6` 仅在当前规则摘要为 `9bec850b41eecf601a0f20cac3448e6f2425185c034eb6f8989cb3226454c247` 时允许恢复。差异仅为路障目标从前方六格内地产扩展为任意无路障地块及相应文案，规则 ID、阶段顺序、效果参数和存档格式保持兼容。其他自定义配置或后续规则变化仍需单独核对，不直接放行。

兼容恢复沿用原完整内部快照，保留地图、资产、手牌及冻结参数、位置、行动顺序、骰子、待处理选择、交易、剩余效果和已确定结果。另建房间后，尚未执行的操作和后续抽取使用当前规则（旧路障手牌也使用当前目标范围），已提交结果和待结算金额不重算；原保存点、规则摘要与公开历史不改写。恢复后的新保存点记录当前规则摘要。

## 接口

新增接口均为 JSON POST，使用独立 DTO／VO：

| 接口 | 输入与输出 |
| --- | --- |
| `/api/archives/query` | `archiveCode`、可选书签版本 `cursor` → 最新进度、对局汇总、书签分页与来源 |
| `/api/archives/history` | `archiveCode`、可选 `gameId`／`turnNumber`／`type`／序号 `cursor` → 公开事实分页；`gameId=lobby` 筛选大厅 |
| `/api/archives/snapshot` | `archiveCode`、可选 `snapshotId` → 当时公开局面与恢复兼容性；省略保存点读最新 |
| `/api/archives/save` | 玩家 `token`、`expectedVersion`、可选 `label` → 当前已提交保存点的手动标记 |
| `/api/archives/restore` | `archiveCode`、`requestId`、可选 `snapshotId`／`playerId` → 新恢复房间会话；默认最新进度与保存时房主角色 |
| `/api/rooms/claim` | 访客 `token`、目标 `playerId`、可选 `name` → 等待房主批准的申请 |

原 WebSocket 命令增加 `assignSeat { claimId }` 与 `continueRecovery`，继续使用命令 ID、预期版本与原回执。增加 `session:identity` 同步已批准角色，原始令牌不进入消息或 URL。玩家私有状态增加固定码和仅房主可见的申请白名单；公开快照增加 `roomId`、恢复配置标志与来源标识。

## 旧数据与部署

Java 启动创建缺失表及身份关联列，批量为旧三表中的当前格式房间补齐标识、会话归属与基线快照，保留原会话及原 Flowable 关联。已有日志只保留实际文字、时间；未保存的行动编号和阶段为空，点击它们只能查看迁移时基线，不补造当时局面，也不补回已经丢失的记录。重复启动不重复建立基线。

这不是旧游戏运行时格式转换。原运行时或 Flowable 关联不兼容时，仍沿用原启动校验拒绝继续。SQLite 导入目标检查包含新增存档及历史表，避免把有档案的库当成空目标。

备份需涵盖六个业务表和同一时点的全部 Flowable 表。首期不增加历史自动清理、六位号回收、导出文件或多实例协调。正式环境数据库迁移及前端生产包部署未在本轮执行。

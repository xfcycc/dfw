# 大富翁 · 好友财富派对

支持 2～6 人的网页版中式大富翁，电脑和手机均可操作，通过房间号加入，独立观战页用于聚会投屏。

## 本地启动

使用 **Java 21、Maven 3.6.3 或以上、Node.js 24.13.1**（项目包含 `.nvmrc`）。后端为 Spring Boot 4.1.1，直接由 Java 启动；Node 用于 Vite 前端及独立数据库工具。`backend/src/main/resources/application.yml` 使用示例数据库地址、账号 `dfw` 和密码占位值 `change-me`，运行前通过 IDE 或进程环境变量设置实际的 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`。先在 IDE 中启动 `backend` 的 `MonopolyApplication`，再在项目根目录启动前端：

```sh
npm ci
npm run dev
```

- 玩家入口：`http://localhost:5173/`
- 同一 Wi-Fi 的其他设备：使用开发服务打印的 `Network` 地址，端口为 `5173`。
- 服务端：`http://localhost:3001`，前端开发服务代理 `/api` 和 `/ws`。
- 玩家房间：`/room/房间号`；公共投屏：`/watch/房间号`。
- 首位玩家创建房间，所有玩家准备后由房主开始。昵称选填，满房最多六人；普通房间开局后新访客只能观战，恢复房间的访客可向房主申请保存角色。
- 点击首页或关闭页面会断开连接并保留席位；房主可移出离线玩家。刷新或重新输入房间号可恢复当前浏览器的原席位。

`npm run dev`（或 `pnpm dev`）只启动 Vite 前端，`npm run dev:web` 也可单独启动前端。后端由 IDE 单独启动，或在另一个终端使用 `npm run dev:server` 编译并直接启动 Java；不要同时启动两个后端。数据库需提前存在，Spring Boot 启动时创建缺失表。修改 Java 代码后先停止后端，再重新执行启动命令；不要覆盖正在运行进程使用的 JAR。前端由 Vite 热更新。启动已打包后端可执行 `npm start`，它等价于 `java -jar backend/target/party-monopoly.jar`；Node 启动包装器和 `dev:all` 已移除。

配置项：`DB_URL`（完整 JDBC 地址）、`DB_USERNAME`、`DB_PASSWORD`、`PORT`（默认 3001）、`APP_ORIGIN`（公开域名）和 `WEB_PATH`（默认 `dist/web`）。`npm start`、`npm run dev:server` 和 IDE 启动的 Java 进程读取其环境变量，不自动加载 `.env.local`；独立数据库工具仍加载 `.env.local`。实际连接资料可以保存在被忽略的 `.env.local`，再通过 IDE 的环境变量配置传入；`.env.local` 不进入 Git 或 Docker 镜像。提交版本的 `application.yml` 使用 `DB_*` 环境变量占位符与示例默认值。也可使用 `SPRING_DATASOURCE_URL`、`SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD` 或同名 Spring 命令行参数覆盖。Docker Compose 使用 `.env`，开发代理可通过 `BACKEND_URL` 指定。

本地数据库维护命令：

```sh
npm run db:init
npm run db:migrate:sqlite
```

`db:init` 只创建缺失的 `dfw` 库及 InnoDB 业务表，不清理现有数据。Java 启动也会自动创建缺失表、补齐缺失的房间身份关联列，并为已有当前格式房间建立历史基线，数据库需先存在。`db:migrate:sqlite` 在停服后把默认 `data/game.sqlite` 的房间、会话摘要和命令回执导入**空目标 MySQL 库**；可追加源文件路径。目标已有对局、身份、存档或历史时拒绝覆盖，全部分批写入在一个事务内提交，失败回滚，原 SQLite 文件保留。

历史数据导入记录（不代表当前格式可迁移）：曾将原本地 SQLite 数据导入 `dfw`：2 个房间、4 个会话、9 条命令回执。原文件 SHA-256 导入前后相同。该记录属于此前存档结构，当前不提供旧运行时迁移或旧引擎恢复。

详细架构与协议见 [架构说明](docs/backend-architecture.md) 和 [联机协议](docs/realtime-protocol.md)。

规则与效果结算架构见 [Flowable 游戏规则与效果结算架构](docs/flowable-game-architecture.md)。当前使用 Flowable 8.0.0 通用流程和效果队列，全部对局统一执行启动时加载的当前规则集。规则拆为 `chance-events.json`、`fortune-events.json`、`card-events.json`、`turn-rules.json`，分别管理完整机会池与补偿订阅、完整财富池、道具及公共回合阶段；配置方法见 [事件规则配置指南](docs/game-rules-dsl.md)。规则版本号、摘要绑定、旧文件和旧引擎分支已经移除，命令信封保持兼容，公开状态增加经济参数、地区和资产榜字段。

修改配置并重启后，进行中对局后续抽取使用当前内容配置；新式手牌保存完整参数和皮肤，出牌按取得时的结果执行，六种无皮肤旧手牌保留兼容配置路径。已经入队的具体效果、待偿债金额和已提交随机结果按原进度恢复，不重新计算。四个行为环境变量为 `GAME_RULES_CHANCE_EVENTS`、`GAME_RULES_FORTUNE_EVENTS`、`GAME_RULES_CARD_EVENTS`、`GAME_RULES_TURN_RULES`，默认分别指向 `classpath:game-rules/` 下同名文件，也支持 `file:` 外部文件。另有独立 `GAME_RULES_ECONOMY` 与 `GAME_RULES_MAP_REGIONS`，见 [金额与地区配置](docs/game-configuration.md)。新局保存本局金额和地图；修改这两类配置不重算已开始的对局。行为结构仍使用当前规则集，勿在进行中对局修改规则 ID 或步骤顺序。

Flowable 与房间存储共用 MySQL 数据源和事务管理器；流程推进、快照和回执在同一短事务中提交。默认启动创建缺失的 `ACT_*` 引擎表并部署固定 BPMN，不启用异步游戏推进。已完成建表的环境可设置 `FLOWABLE_SCHEMA_UPDATE=false`，启动时仅校验引擎表结构。备份恢复应包含同一时点的整个数据库，包括 Flowable 表。启动仍校验流程实例、任务、决策关联和阶段游标，错配时拒绝继续；不迁移旧格式存档、不自动重建流程或清理现有数据库。

## 已实现的玩法

2026-10-18 新增十五张道具与四个事件：A.T.力场、制衡、发现、闷棍、等价交换、迟缓、任意两人换位、神威、手牌抹杀、地爆天星、尸鬼封尽、暗影步、传送、黑洞及陨星，以及宝藏、演唱会、ROOM全员换位和全员补给。地产附加效果统一在名称后显示✦，详情说明层数、金额及暂停状态；手牌上限随尸鬼封尽降低。逐项文案、概率、结算及验证边界见[新增内容说明](docs/content/expansion-2026-10-18.md)。

新局默认金额统一 ×2，每人开局 ¥12,000、两张随机道具。掷一枚六面骰子，顺时针移动，向前或后退经过、到达起点，或在起点使用原地停留效果，均获得 ¥2,000。各项支持最终固定金额覆盖，建造与租金由实际地价计算，不重复乘倍率。游戏持续到只剩一名未破产玩家。

新局四角为起点、两个轮换活动角、监狱，机会与财富总数保持并移到边上，补充特殊格随机从可用普通格中选择，特殊格之间至少隔一个普通格。每边选用同一地区的地名池，默认有三角洲、大陆现实、宝可梦关都／城都／丰缘／神奥、原神蒙德／璃月、火影忍者、西游记、世界城市、原创烟火夜市／海岛度假／奇幻小镇，共 14 组；短池自动添加编号后缀（如 `·2号`）。基准地价 400 / 600 / 800 / 1200 / 1600 五档，默认 ×2 后为 800 / 1200 / 1600 / 2400 / 3200。每边尽量均衡随机分配，不足五块或不足整组时随机选取剩余价档。地区仅用于命名。每局地图有独立种子，游戏中的骰子、事件和抽卡不使用地图种子。

- 停在无主地产可以买下或放弃；新买的地本次不立即建房。
- 只有停在自己的未抵押地产时可以升一级，最高三级；每块地每回合最多升级一次，每级造价为地价的 50%。
- 新局基础路费为地价的 25%，0～3 级倍率为 1 / 3 / 6 / 10，即实际地价的 25% / 75% / 150% / 250%。比例保存到本局经济快照，已有对局保持其保存比例，快照缺失比例时保留原 10%；固定租金覆盖优先，抵押地产不收费。
- 卖未抵押建筑一级默认返还实际建造成本的 50%；土地加建筑可整体抵押取得总估值的 50%，保留建筑并停收租金，赎回需付抵押时估值的 55%，基数不随拆房变化并随产权转移。抵押建筑不能单独卖出；土地与现有建筑可整套出售给系统，默认回收当前成本估值的 70%，无需先卖房；已抵押时扣除固定赎回费用，回收款不足须现金补差价，现金不足不能出售。整售后产权归还银行、建筑归零；原土地回收金额覆盖继续作用于土地部分。
- 强制费用先选择支付方式，即使现金足够也不直接扣款。可以自行选择资产抵押或变现，再手动确认付款；欠玩家时允许协商地产抵债或向第三人出售资产筹款，抵扣金额由双方确认，可抵清或部分抵扣。系统费用须先自行抵押或出售全部可抵押地产；现金加各地产最高银行变现所得仍不足时才允许确认清算，有能力偿清时不可申请破产。最高变现所得比较抵押、整售及先卖房再变现，已抵押地产只计扣除固定赎回费用后的正净额。清算后地产回到银行、建筑归零、手牌作废，可变现金额用于向玩家债权人偿还至多欠款。
- 停在监狱或触发休息事件，跳过下一次行动；持有解控卡时在限制施加处选择使用或放弃，不占主动次数。
- 机会和财富采用已确认的机制概率、金额档、去重参数和匹配皮肤抽取。运行素材共247条：机会93、财富63、道具91；财富12条再次行动素材停用，启用235条。三池按完整效果独立权重抽取，再等概率选择匹配皮肤；新增道具31%、原道具69%、UR道具合计5%，具体概率见内容运行说明。排名目标在事件开始锁定，并列随机选择；赌博、免费升级和自家毁楼需要本人选择。
- 每回合最多触发一次机会或财富抽取；事件移动仍结算地产、监狱、起点与路障。
- 向前或后退经过、到达起点，或在起点使用原地停留效果，均获得本局起点收入，并按本局人数补给道具：2 人局 1 张，3 人及以上对局 2 张（含已淘汰玩家）；超出手牌上限时，移动完成后先整理手牌，再继续原落点结算。移动到起点只领取一次奖励，开局站在起点不自动领奖。
- 局内采用白色地图工作台，方形地块默认展开，无缩放、展开、全图和定位控件。中央左侧顶部为城市新鲜事，实时与历史共享入口，左侧底部为聊天输入区，仅保留发送消息按钮；右侧上方为资产排行，离线状态与移出并清算入口紧跟玩家名字，点击头像在弹窗查看该玩家地产；下方为紧凑工作台，集中显示本人排名、现金、净资产、当前行动、待办入口及报价提醒，并以完整图片按钮提供我的资产／交易／掷骰／结束行动（固定两列两行），资产明细复用原弹窗；下方一整行六张手牌横跨两列，布局铺满地图内圈，长列表独立滚动。聊天与道具目标、效果、事件和结算一起进入公开记录，玩家姓名按颜色标记。实时动态最新在下，查看旧记录时暂停跟随。买地、升级、付款、防御和私人选择使用临时弹窗，关闭可先观察局势并从工作台继续；报价草稿、卡牌目标与私人选择勾选在收起后保留。交易手动打开独立弹窗，报价到达持续提醒，成交预览以“我”为先。声音设置位于右上角实时同步旁。
- 玩家可在房间内选择 20 种角色形象，包含皮卡丘、伊布、忍者影丸和蔡徐坤；棋盘位置显示姓名和动态小人，本人位置与当前行动者另有醒目标识。地产名称在上、金额在下，拥有者小头像位于右上角，中间留给棋子；所属玩家颜色环绕，建筑等级与装饰随升级增强。起点、机会、财富和监狱使用独立生成的图片。掷骰、结束行动、交易和我的资产使用工作台完整图片按钮。点击手牌后，在弹窗内选择目标或参数，再确认使用。
- 路障可在附近 6 格内选择一个无路障地块放置（沿环形棋盘前后各 6 格，不含当前格），包括起点、机会、财富、监狱和活动格；截停后照常结算落点，免疫时继续通过且保留路障。
- 道具包括替代掷骰（固定步数与遥控骰子）、路障、拆房、换位、免租、主动位移、掷骰加码、免费升级、付款减半、解控、抢夺手牌、即时现金、UR指定全拆和UR免费直升满级。每回合掷骰前最多主动使用一张，负位移替代本次掷骰，加码合成一次连续移动。免费升级取消或没有合法目标时保留卡；抢夺空手对手保留卡与次数。
- 强制费用先处理自动免单或手动选择免租／减半／放弃，再筹款、资产抵债和手动支付；减免额向下取整，房东只收减免后的余额。本笔费用不重复防御，租金翻倍先于防御。
- 手牌默认上限六张，尸鬼封尽可降至最低一张；超限后从原牌与全部补给中恰选当前上限数量，其余每张基准 200（默认 400）折现。选择保存候选和父费用等待位置，确认与折现一次提交；具体皮肤、牌型及超限候选仅本人可见，当前持有手牌数量公开。
- 交易仅涉及现金与地产，建筑及固定赎回费用随地产转移。当前行动者在移动前或落点处理完成后发起，玩家债务的付款人也可在费用结算中发起；双方确认后原子交换。以线下游玩为主，玩法选择、偿债和报价均不设倒计时，报价等待主动接受、拒绝或取消，等待期间冻结其他游戏操作。
- 所有玩家和观众看到相同的净资产与并列名次。净资产按现金及土地建筑成本计，抵押地产减固定赎回费用，单地剩余权益最低为零。
- 房主可在大厅添加简单、普通、困难机器人，调整难度或移出机器人；机器人自动准备，占用普通玩家席位，总人数仍为 2～6 人。机器人使用相同规则和存档流程，支持交易、道具、付款与全部活动输入，决策只读取公开局面与本人私有信息。策略与验证边界见 [机器人说明](docs/game-bots.md)。
- 无拍卖、账号注册、岔路或 3D 场景。

后端规则位于 `backend/src/main/java/com/dfw/domain/`，四份行为配置与两份经济／地区配置位于 `backend/src/main/resources/game-rules/`，估值公式在 `Rules.java`，地图生成位于 `MapService.java`。前端 `src/shared/rules.ts` 保留展示常量、棋盘坐标和地图算法对照。调整规则时核对前端展示值；结算以 Java 后端为准。本轮内容机制已接入源码；通用被动系统、多地块聚合和 UR 素材仍属于后续设计。

## 联机、身份和隐私

服务端决定随机结果、资金、产权和胜负。每个命令带唯一 ID 和预期版本；同一房间串行执行，重复命令返回原回执，旧版本操作拒绝并重新同步。

`room:snapshot` 只包含公开地图、玩家、操作阶段和最近公开记录。`player:private` 只发送给对应玩家的当前连接，包含完整手牌卡面、主动道具使用状态、本人参与的报价和选择窗口。私人补给的整张事件卡面也仅本人可见；抢夺双方只收到被转移的那张牌。观战会话没有操作权限，可查看公开的持有卡牌数量，但不接收具体手牌卡面或可操作的报价对象。报价发起、具体现金与地产、同意／拒绝／取消、关联欠款和成交抵扣余额均进入公开记录，观众可查看双方及付款、减免的主体和收款方。公开记录描述已发生的地图、资金、事件及已使用道具的目标与效果；补给不公开具体卡牌，起点补给按本局人数发放：2 人局 1 张，3 人及以上对局 2 张（含已淘汰玩家）。`POST /api/rooms/logs` 凭当前房间会话分页读取本局全部公开记录，不返回私人审计内容或存档码。

普通玩家会话使用 256 位随机令牌；首次恢复的会话由共享码、随机请求 ID 和新房间 ID 派生，以便重试返回同一身份。浏览器保存原始令牌，MySQL 只保存摘要，令牌不进入 URL。同一角色只允许一个有效操作连接。原房间自动回座依赖浏览器数据；换设备可使用固定存档码另建恢复房间，由新房主分配保存角色，原房间的角色身份不会按昵称自动认领。

每次有效操作将整个房间快照和命令回执写入同一 MySQL InnoDB 事务，提交成功后才广播。失败保留原状态。非操作人离线可以继续，轮到离线玩家或等待离线交易对象回应时暂停，报价和债务保留到重连继续处理。房主离线后移交给最早加入的在线玩家，全员离线保留进度。

服务重启后标记所有席位离线，重新认证后继续原有落点选择、偿债和交易。未结束房间不会自动清理。

数据库使用 MySQL 8.0 或以上；本机实际验证版本为 8.0.38。六个业务表统一使用 InnoDB 与 utf8mb4，房间快照和回执为 LONGTEXT JSON，身份与命令主键使用区分大小写的 ASCII 比较。新增档案、历史、进度快照按永久 `roomId` 关联，六位房间号首期仍不回收。Flowable 在同一库中维护流程定义、执行和任务表。后端不再依赖 SQLite JDBC；`node:sqlite` 仅用于可选旧文件导入。

首版仍采用单个游戏服务进程，多房间分别串行处理；Hikari 最大连接数为 4，每笔提交为短事务，不在事务内等待网络推送。不能仅因换成 MySQL 就同时启动多个实例管理相同房间。

## 历史和存档

- 首页“历史与恢复”或房间“历史回顾”打开 `/archives`；浏览器自动保存参与过的房间与固定存档码。
- 每次成功提交自动保存完整进度和全部事实，实时动态仍只显示最近 100 条。手动存档标记当前保存点并可填写备注，同一房间固定码不变，再开新局保留旧对局历史。

- 固定码是共享恢复凭证，不另设账号或个人恢复码。格式或玩法规则不兼容时保留历史回顾并说明原因。具体接口、迁移和验证边界见 [固定存档码与历史恢复](docs/game-archives.md)。

## 自有服务器部署

`Dockerfile` 内含生产构建步骤；执行 Docker 构建会执行前端 build，本轮未执行。部署者应在具备构建授权的环境或 CI 中完成：

1. 安装 Docker Compose，准备域名和 TLS 证书。
2. 将 `.env.example` 复制为 `.env`，设置独立的 `DB_PASSWORD` 和 `MYSQL_ROOT_PASSWORD`，应用用户默认 `dfw`；把 `APP_ORIGIN` 改为实际 HTTPS 域名。该值用于 WebSocket Origin 校验；本地开发默认同源。不要将本地 root 配置复制进生产镜像。
3. 执行 `docker compose up -d --build`，包含独立 MySQL 8.4 服务，游戏只映射至服务器的 `127.0.0.1:3001`，数据库保存在 `mysql-data` 卷且不映射数据库公网端口。
4. 按 `deploy/nginx.conf.example` 配置反向代理，替换域名和证书路径。`map` 配置位于 Nginx 的 `http` 上下文。检查配置后重载 Nginx。
5. 用两个设备创建并加入房间、开局，再用第三个页面观战；检查 WSS、断线恢复和服务重启恢复。

不要在生产环境使用 Vite 开发服务器。生产服务由 Java 同时提供编译后的网页、HTTP 接口和原生 WebSocket。检查接口为 `GET /api/health`。

使用 MySQL 一致性备份工具，例如 InnoDB 的 `mysqldump --single-transaction`；恢复或旧数据切换应先停止游戏服务。旧 `game-data` 卷与本地 SQLite 文件不自动删除，完成数据导入前应保留。不要把进行中对局的数据库文件和浏览器身份令牌公开分享。

## 图片存储

所有项目图片（运行素材、生成素材、文档插图及验收截图）统一存放在现有阿里云 OSS，项目工作区仅保存 URL、提示词及来源元数据，不保留图片二进制。

- `src/web/image-assets.json`：原公共图片路径到 HTTPS URL 的映射，组件经 `imageUrl()` 读取；原路径仅作为资源标识。
- `src/web/card-illustrations.json` 与 `src/web/card-frames.json`：独立卡面和卡框的云端 URL。
- `generated-assets/cloud-images.json`：本次全部迁移图片的原路径、云端 URL、压缩前后字节数、尺寸、摘要及逐项远端校验记录。旧素材清单中的路径和原图摘要保留用于追溯，当前云端文件以此清单为准。

新增图片先在临时目录生成和压缩，再上传现有 PicGo/OSS，核对远端状态、类型、大小和摘要后更新映射。保留原尺寸与透明度；已有 WebP 不重复有损编码，SVG 保持矢量。`scripts/prepare-activity-art.py` 从云端读取图集，只向系统临时目录输出待上传素材，不再向 `public` 写图片。

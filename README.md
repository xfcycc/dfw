# 大富翁 · 好友财富派对

支持 2～6 人的网页版中式大富翁，电脑和手机均可操作，通过房间号加入，独立观战页用于聚会投屏。

## 本地启动

使用 **Java 21、Maven 3.6.3 或以上、Node.js 24.13.1**（项目包含 `.nvmrc`）。后端为 Spring Boot 4.1.1，Node 仅用于前端开发及联机冒烟。本地 MySQL 默认连接 `127.0.0.1:3306/dfw`，本次提供的连接资料已写入被忽略的 `.env.local`。安装依赖后，在项目根目录启动：

```sh
npm ci
npm run dev
```

- 玩家入口：`http://localhost:5173/`
- 同一 Wi-Fi 的其他设备：使用开发服务打印的 `Network` 地址，端口为 `5173`。
- 服务端：`http://localhost:3001`，前端开发服务代理 `/api` 和 `/ws`。
- 玩家房间：`/room/房间号`；公共投屏：`/watch/房间号`。
- 首位玩家创建房间，所有玩家准备后由房主开始。昵称选填，满房最多六人，游戏开始后新访客只能观战。
- 点击首页或关闭页面会断开连接并保留席位；房主可移出离线玩家。刷新或重新输入房间号可恢复当前浏览器的原席位。

后端开发启动会先创建缺失的数据库与表、编译再运行；修改 Java 代码后先停止后端，再重新执行启动命令；不要覆盖正在运行进程使用的 JAR。前端由 Vite 热更新。单独启动已打包后端可执行 `npm start`。

配置项：`DB_URL`（完整 JDBC 地址）、`DB_USERNAME`、`DB_PASSWORD`、`PORT`（默认 3001）、`APP_ORIGIN`（公开域名）和 `WEB_PATH`（默认 `dist/web`）。`npm start`、开发服务和数据库工具自动加载项目根目录 `.env.local`；直接使用 `java -jar` 时需要自行传入环境变量。`.env.local` 不进入 Git 或 Docker 镜像。提交版本的 `application.yml` 使用 `DB_*` 环境变量占位符。若本地工作区改为固定数据源，隔离启动应使用 `SPRING_DATASOURCE_URL`、`SPRING_DATASOURCE_USERNAME`、`SPRING_DATASOURCE_PASSWORD` 或同名 Spring 命令行参数显式覆盖；仅传入 `DB_*` 不会覆盖固定配置。Docker Compose 使用 `.env`，开发代理可通过 `BACKEND_URL` 指定。

本地数据库维护命令：

```sh
npm run db:init
npm run db:migrate:sqlite
```

`db:init` 只创建缺失的 `dfw` 库及三张 InnoDB 表，不清理现有数据。Java 启动也会自动创建缺失表，数据库需先存在。`db:migrate:sqlite` 在停服后把默认 `data/game.sqlite` 的房间、会话摘要和命令回执导入**空目标 MySQL 库**；可追加源文件路径。目标已有任何业务记录时拒绝覆盖，全部分批写入在一个事务内提交，失败回滚，原 SQLite 文件保留。

本次已将原本地 SQLite 数据导入 `dfw`：2 个房间、4 个会话、9 条命令回执。原文件 SHA-256 导入前后相同。已有浏览器身份无需重新加入；更新后的 Java 后端启动后可恢复原席位。

详细架构与协议见 [架构说明](docs/backend-architecture.md) 和 [联机协议](docs/realtime-protocol.md)。

规则与效果结算架构见 [Flowable 游戏规则与效果结算架构](docs/flowable-game-architecture.md)。当前已接入 Flowable 8.0.0 通用流程与效果结算器，新开对局通过一个通用等待任务处理原有操作，六种道具及主动交易进入效果队列；已有进行中快照没有 `runtime` 时继续使用旧引擎。当前新局使用 `classic-v2` 配置阶段与六种道具，条件 AST、发动窗口、主动次数和效果组合从版本 JSON 加载；进行中的 `classic-v1` 对局保留原路径。前端命令及公开/私人状态协议保持兼容。实际配置方法见 [回合阶段与道具规则配置](docs/game-rules-dsl.md)。全图事件、持续状态、随机分支和补偿仍为后续设计。

Flowable 与房间存储共用 MySQL 数据源和事务管理器；流程推进、快照和回执在同一短事务中提交。默认启动自动创建缺失的 `ACT_*` 引擎表并部署固定 BPMN，不启用异步游戏推进。已完成建表的环境可设置 `FLOWABLE_SCHEMA_UPDATE=false`，启动时仅校验引擎表版本。备份和恢复应包含同一时点的整个数据库，包括 Flowable 表；不要只恢复三个业务表。配置对局固定规则版本和文件摘要；发布新版本时须保留旧文件，以便恢复旧局。本轮主要接口验证使用独立临时库，验证记录见下文。

## 已实现的玩法

每人开局 ¥6,000、两张随机道具。掷一枚六面骰子，顺时针移动，正向经过或到达起点获得 ¥1,000。游戏持续到只剩一名未破产玩家。

| 人数 | 地图格数 |
| --- | --- |
| 2 / 3 / 4 / 5 / 6 | 24 / 28 / 32 / 36 / 40 |

四角为起点、机会、财富、监狱。额外机会格从第 1 或第 3 边段选择，额外财富格从第 2 或第 4 边段选择；特殊格之间至少间隔一个普通格。其他地产按街区名称池抽取，800 / 1,200 / 1,600 三档价格在各边段均衡随机分配。每局地图有独立种子，游戏中的骰子、事件和抽卡不使用地图种子。

- 停在无主地产可以买下或放弃；新买的地本次不立即建房。
- 只有停在自己的未抵押地产时可以升一级，最高三级；每块地每回合最多升级一次，每级造价为地价的 50%。
- 基础路费为地价的 10%，0～3 级倍率为 1 / 3 / 6 / 10。抵押地产不收费。
- 卖一级房返还地价的 25%；无建筑地产抵押获得 50%，赎回支付 55%。无建筑地产卖出返还 50%，已抵押地产不再返款。
- 现金不足但可变现资产足够时进入偿债阶段，只能卖房、抵押、卖地，筹足自动支付；全部变现仍不足则清算淘汰，可变现金额用于支付债权人，地产回到银行、建筑归零、手牌作废。
- 停在监狱或触发休息事件，跳过下一次行动。
- 机会等概率触发 +300、−300、前进三格、后退三格、休息一次或抽一张道具；财富等概率触发 +300 / +500 / +800 / +1,000 或抽一张 / 两张道具。
- 每回合最多触发一次机会或财富抽取；事件移动仍结算地产、监狱、起点与路障。
- 六种道具：遥控骰子、路障、停留、免租、拆房、换位。每回合掷骰前最多主动使用一张，免租在收费时单独选择。
- 交易仅涉及现金与地产，建筑和抵押状态随地产转移。当前行动者在移动前或落点处理完成后发起，双方确认后原子交换；等待期间冻结其他游戏操作，正常连接下 60 秒无回应取消。
- 无机器人、拍卖、账号注册、岔路或 3D 场景。

后端规则位于 `backend/src/main/java/com/dfw/domain/`，配置阶段和六种道具定义位于 `backend/src/main/resources/game-rules/classic-v2.json`，经济常量集中于 `Rules.java`，地图生成位于 `MapService.java`。前端的 `src/shared/rules.ts` 保留展示常量、棋盘坐标和原地图算法用于跨语言对照。调整规则时同时核对前端展示值；结算以 Java 后端为准。

## 联机、身份和隐私

服务端决定随机结果、资金、产权和胜负。每个命令带唯一 ID 和预期版本；同一房间串行执行，重复命令返回原回执，旧版本操作拒绝并重新同步。

`room:snapshot` 只包含公开地图、玩家、操作阶段和公开记录。`player:private` 只发送给对应玩家的当前连接，包含其手牌、主动道具使用状态及本人参与的报价。观战会话没有操作权限，不接收手牌、卡牌数量或私人报价。公开记录只描述已发生的地图和资金结果，抽卡不记录种类、数量。

玩家会话使用 256 位随机令牌，本地浏览器保存原始令牌，MySQL 只保存令牌摘要。令牌不进入 URL；同一玩家打开新操作连接时替换旧连接。免注册恢复依赖当前浏览器数据，不支持跨设备找回或清除浏览器数据后恢复原席位。

每次有效操作将整个房间快照和命令回执写入同一 MySQL InnoDB 事务，提交成功后才广播。失败保留原状态。非操作人离线可以继续，轮到离线玩家或等待离线交易对象回应时暂停；交易倒计时也暂停。房主离线后移交给最早加入的在线玩家，全员离线保留进度。

服务重启后标记所有席位离线，重新认证后继续原有落点选择、偿债和交易。未结束房间不会自动清理。

数据库使用 MySQL 8.0 或以上；本机实际验证版本为 8.0.38。三个业务表统一使用 InnoDB 与 utf8mb4，房间快照和回执为 LONGTEXT JSON，身份与命令主键使用区分大小写的 ASCII 比较，保持旧版语义。Flowable 在同一库中维护流程定义、执行和任务表。后端不再依赖 SQLite JDBC；`node:sqlite` 仅用于可选旧文件导入。

首版仍采用单个游戏服务进程，多房间分别串行处理；Hikari 最大连接数为 4，每笔提交为短事务，不在事务内等待网络推送。不能仅因换成 MySQL 就同时启动多个实例管理相同房间。

## 自有服务器部署

`Dockerfile` 内含生产构建步骤；执行 Docker 构建会执行前端 build，本轮未执行。部署者应在具备构建授权的环境或 CI 中完成：

1. 安装 Docker Compose，准备域名和 TLS 证书。
2. 将 `.env.example` 复制为 `.env`，设置独立的 `DB_PASSWORD` 和 `MYSQL_ROOT_PASSWORD`，应用用户默认 `dfw`；把 `APP_ORIGIN` 改为实际 HTTPS 域名。该值用于 WebSocket Origin 校验；本地开发默认同源。不要将本地 root 配置复制进生产镜像。
3. 执行 `docker compose up -d --build`，包含独立 MySQL 8.4 服务，游戏只映射至服务器的 `127.0.0.1:3001`，数据库保存在 `mysql-data` 卷且不映射数据库公网端口。
4. 按 `deploy/nginx.conf.example` 配置反向代理，替换域名和证书路径。`map` 配置位于 Nginx 的 `http` 上下文。检查配置后重载 Nginx。
5. 用两个设备创建并加入房间、开局，再用第三个页面观战；检查 WSS、断线恢复和服务重启恢复。

不要在生产环境使用 Vite 开发服务器。生产服务由 Java 同时提供编译后的网页、HTTP 接口和原生 WebSocket。检查接口为 `GET /api/health`。

使用 MySQL 一致性备份工具，例如 InnoDB 的 `mysqldump --single-transaction`；恢复或旧数据切换应先停止游戏服务。旧 `game-data` 卷与本地 SQLite 文件不自动删除，完成数据导入前应保留。不要把进行中对局的数据库文件和浏览器身份令牌公开分享。
